## 1. ภาพรวม

- **[Fact]** งานคู่ (2 คน) · เว็บแอป Flask + MySQL · ส่ง 3 ครั้ง รวม 100 คะแนน คิดเป็น 40% ของวิชา
- **[Fact]** อาจารย์แจกเทมเพลต: หน้าเว็บ + API + โครงฟังก์ชันใน `db.py` (ว่างไว้) นิสิตต้องทำ: ออกแบบ ER + `schema.sql`, เขียน SQL ในฟังก์ชัน CRUD, เขียน SQL ของรายงาน (JOIN/GROUP BY/subquery), เชื่อม DB (user/password), ป้องกัน SQL injection ด้วย parameter
- **[Fact]** ใช้ MySQL ของรายวิชา หรือ local ในเครื่องตัวเองก็ได้ (กลุ่มนี้ใช้ local)
- **[Fact]** ให้คะแนนที่ **ความเข้าใจ database schema และคำสั่ง SQL เป็นหลัก** นิสิตที่เก่งเว็บเพิ่ม feature เองได้
- **[Fact]** โจทย์ของกลุ่มนี้ = **โจทย์ที่ 4 ระบบร้านค้าออนไลน์ขนาดเล็ก** (ต้องเช็คในไฟล์คะแนนของอาจารย์ว่ากลุ่มได้หัวข้อนี้จริง)

## 3. ข้อกำหนดโครงสร้างฐานข้อมูล (บังคับทุกโจทย์)

1. ตาราง 5–7 ตาราง มี PRIMARY KEY ทุกตาราง
2. ความสัมพันธ์ M:N อย่างน้อย 2 จุด (ต้องมีตารางเชื่อม)
3. self-reference อย่างน้อย 1 จุด "ตามที่ระบุในแต่ละโจทย์"
4. FOREIGN KEY ถูกต้อง
5. รองรับรายงานบังคับ 3 รายการ ซึ่งต้อง **JOIN ตั้งแต่ 3 ตารางขึ้นไป**
6. sample data อย่างน้อยตารางละ 5–10 แถว เพื่อทดสอบรายงาน

**[Analysis]** ข้อ 3: โจทย์ 4 ไม่ได้ระบุ self-reference ไว้ และ `schema.sql` ใน template ร้านค้าก็ไม่มี น่าจะไม่บังคับสำหรับโจทย์นี้ แต่ยังไม่ได้ยืนยัน → ให้ถามอาจารย์

## 4. ข้อกำหนดเฉพาะโจทย์ 4

**เอนทิตีที่ต้องมี [Fact]:** `customer`, `product`, `shop_order`, `order_line` (M:N #1: order × product), `review` (M:N #2: customer × product), `payment` (weak entity ของ shop_order) · นิสิตออกแบบคอลัมน์ คีย์ ชนิดข้อมูลเอง

**กติกาของระบบ [Fact]**
1. ลูกค้าสั่งได้หลายออเดอร์ แต่ละออเดอร์มีหลายรายการสินค้า
2. สินค้าหนึ่งอยู่ในหลายออเดอร์ และ **ต้องเก็บจำนวนและราคาต่อหน่วย "ขณะสั่ง"**
3. ลูกค้ารีวิวสินค้าได้ (คะแนน + ความเห็น) — ความสัมพันธ์ลูกค้า × สินค้า
4. แต่ละออเดอร์มีการชำระเงิน
5. ต้องเก็บสต็อกสินค้าและสถานะออเดอร์

**รายงานบังคับ 3 รายการ [Fact]**
1. สินค้าขายดี ตามจำนวนที่ขายได้ — join + `GROUP BY` + `SUM(qty)`
2. ลูกค้าที่มียอดซื้อรวม **มากกว่าค่าเฉลี่ยของลูกค้าทุกคน** — **subquery กับ `AVG`**
3. สินค้าที่คะแนนรีวิวเฉลี่ย **ตั้งแต่ 4 ขึ้นไป** — `GROUP BY` + `AVG` + `HAVING`

**ฟีเจอร์พิเศษเฉพาะกลุ่ม [Fact]:** อาจารย์สุ่ม/กำหนด 1 อย่างต่อกลุ่ม (ตัวอย่าง: ระบบ VIP/ส่วนลด, โปรโมชันตามช่วงเวลา, แจ้งเตือนเกินกำหนด, Top 10 + กราฟ, ค้นหาขั้นสูง, สถิติรายเดือนบน dashboard) → **กลุ่มนี้ยังไม่ทราบว่าได้อะไร**

## 6. ความเข้าใจรายบุคคล (สำคัญ)

- **[Fact]** อนุญาตให้ใช้ AI แต่นิสิตต้องเข้าใจโค้ดและ SQL **ทุกบรรทัดที่ส่ง**
- **[Fact]** ตัวอย่างคำถาม: "คำสั่งนี้ทำงานอย่างไร", "ทำไมต้อง JOIN ตรงนี้", "ถ้าจะเพิ่มเงื่อนไขนี้ (เช่น กรองเฉพาะเดือนนี้) ต้องแก้ตรงไหน", "ทำไมตารางนี้ต้องมี FK ตรงนี้ / ทำไมใช้ JOIN แทนการเก็บข้อมูลซ้ำ", คำถามนอกเหนืองาน เช่น "ถ้าอยากเพิ่ม report แบบนี้ ควรมี table อะไรเพิ่ม"
- **[Fact]** ถ้านิสิตคนใดตอบเรื่องงานของตนไม่ได้ **หักคะแนนเฉพาะคนนั้น**
- **[Fact]** แต่ละกลุ่มมีฟีเจอร์พิเศษต่างกัน ผลงานเหมือนกันผิดปกติจะถูกตรวจสอบ การคัดลอก schema/โค้ดของกลุ่มอื่น = ทุจริต

**[Analysis] แนวทางสำหรับ Claude ที่ช่วยงานนี้:** กลุ่มต้องการ **ออกแบบ schema และเขียน SQL ใน `db.py` เองและเข้าใจเอง** (ผู้ใช้ระบุชัดเจน) → Claude ควรอธิบาย ให้คำใบ้ รีวิว และเตรียมคำตอบสำหรับถามรายบุคคล ไม่ใช่เขียนให้ทั้งหมดโดยผู้ใช้ไม่เข้าใจ

## 7. ประเด็นที่อาจารย์น่าจะถาม (เตรียมคำตอบ) — [Analysis]

- ทำไมเก็บ `unit_price` ใน `order_line` ทั้งที่มี `product.price` (ราคา ณ ตอนสั่ง — กติกาข้อ 2)
- ทำไม `order_line`/`review` ใช้ composite PK
- ทำไม `payment` เป็น 1:1 (`order_id UNIQUE`) และทำไม `payment.amount` ซ้ำกับผลรวม `order_line`
- รายงานลูกค้ายอดเกินค่าเฉลี่ย: subquery ทำอะไร, ทำไมต้องหายอดรวมต่อลูกค้าก่อนแล้วค่อย `AVG`
- `WHERE` ต่างจาก `HAVING` อย่างไร (ใช้ใน report 3)
- ถ้าเพิ่มเงื่อนไข "เฉพาะเดือนนี้" ต้องแก้ตรงไหน
- ทำไมใช้ `%s` แทนการต่อสตริง (SQL injection)
- ทำไมลบลูกค้าที่มีออเดอร์ไม่ได้ (FK ป้องกันข้อมูลกำพร้า)
